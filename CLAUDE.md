## DryDock-specific working agreements (overrides on top of the universal CLAUDE.md)

- **Don't add another auto-sync trigger** without checking [components/useAutoSync.ts](components/useAutoSync.ts) first. The dashboard mounts it one-shot; `/backlog` mounts it with `intervalMs: 30_000`. Both share the server-side `inFlightSync` mutex so duplicate triggers are harmless but wasteful.
- **Backlog status `dropped` is legacy** — the UI no longer exposes Drop. Existing rows with `status='dropped'` still get filtered out of the Apple Notes push, but new user actions are limited to Burn down / Mark done / ✏️ Edit / 🗑️ delete.
- **Don't loosen Apple Notes' `irreversible done` rule.** A checked box in Notes promotes the DB to `done`; un-checking is intentionally ignored. The user can re-open via UI explicitly.
- **Don't add a second canonical-note discovery path.** The `apple_notes_note_id` setting is authoritative; everything else is fallback. If you find yourself adding new search heuristics, write a test first that proves the id-stable path can't handle the case.

## Universal lessons learned here (mirrored to [coding-best-practices/CLAUDE.md](../coding-best-practices/CLAUDE.md))

These generalize beyond DryDock and live in both files by standing instruction. Keep the two copies in sync — edit both in the same pass.

### 2026-07-26 (telemetry track: plan → 6 epics → 2 review rounds)

- **"A failure that looks like success" is a bug class worth reviewing for by name.** One session shipped six instances, none caught by a passing suite: health that described the *incremental slice* rather than the source (so an overnight no-op badged a populated card "no data"); a sync that stamped its success timestamp after failed writes; a route that returned a `mirror` status field the UI never read (green "Synced" over a tick where every remote write failed); a bidirectional-reopen rule that re-closed the issue in the same pass because the push held a snapshot taken before the pull wrote; an importer that overwrote the hand-written body it had just imported; and a collector whose caught failure was discarded by its own background caller. The shared shape: the *unhappy* path produces output indistinguishable from the happy one. Ask of every status, health, and sync surface — "what does this render when the underlying thing failed?" — and make the answer different from what it renders on success.
- **Validate a hand-rolled binary/format parser against the real corpus before trusting it, using records that carry both the parsed field and an authoritative one.** Decoding Apple's `attributedBody` typedstream, the check was 4,000 messages having BOTH `text` and `attributedBody`: 4,000 exact matches, 0 mismatches — *then* the decoder was wired in. The same pass measured how much of the corpus actually needs it (52% of messages have a NULL `text`), which reclassified it from "fragile fallback" to "the main path". Both numbers are cheap to get and change the design; guessing either would have shipped a channel that silently captured half of everything.
- **Never run a production build while a dev server is running on the same tree.** `npm run build` rewrites `.next/` under the live server, which then 500s on every route with `Cannot find module './NNN.js'` — and the error points at webpack internals, not at what you did. Build in a separate checkout, or stop the dev server first and restart it after.
- **A test fixture root must mirror the real directory layout whenever the code derives a sibling or parent path from it.** A bare `mkdtemp()`-created root made a `dirname(root)/archived_sessions` lookup resolve to `$TMPDIR/archived_sessions` — shared mutable state across every test run on the machine. Build the fixture as `<tmp>/<the-real-parent>/…` so derived paths stay inside the sandbox.
- **A default parameter pointing at a real user path will have your tests reading the developer's own data.** Two readers defaulted to `~/.gemini/antigravity-cli` and `~/Library/Messages/chat.db`; any test that didn't override them was silently reading a personal message archive. Every test passes an explicit, deliberately non-existent path — and the parameter is absolute rather than derived, so a fixture can't accidentally resolve onto the real one.
- **A first run that scans everything must not block a page load — background it and report that it's running.** A cold usage ledger took 83 seconds to build (270 large session logs, none skippable by the mtime pre-filter), which is a broken dashboard on a phone. Answering from the store as it stands (~140ms) plus a `collecting` flag lets the UI say "still reading" instead of rendering a cold store's zeros as fact — the same looks-like-success trap above.
- **`gh api repos/O/R/pulls/N/reviews` rejects an inline comment on a file that isn't in the diff** — 422 `Path could not be resolved`, with no indication of which path. Anchor review comments only on changed files; when the observation is about an unchanged consumer, comment on the changed producer and describe the consumer in the body.

### 2026-08-05 (dependency sweep + orphan-branch triage)

- **A long-unmerged branch's ID space gets silently reused — triage before merging, never merge assuming the IDs are still free.** A May-24 docs branch carried ten issue entries (`DD-009`…`DD-018`) and four backlog items (`DD-BL-36`…`39`). Every single ID had since been reassigned to unrelated work: the branch's `DD-016` was "Settings page double-fetch", main's is "next pinned at 15.5.18 / CVE batch". Merging it would have produced two rows per ID describing different bugs, in the exact files future sessions are told to trust. The reuse also happens *while you work* — a parallel session claimed `DD-020` mid-triage, invalidating the numbering derived twenty minutes earlier. Re-derive the ID space from the file at the moment of writing, not from an earlier read.
- **Triage an old branch against the code, not against its own descriptions.** Of those ten findings, four still reproduced, one was self-marked resolved, one had become documented-by-design, and four had been quietly fixed by unrelated work — an empty-array guard on a percentile index, a combined mount effect, a back-link on the detail page. Nothing in the branch recorded any of that. The commit message describes the world on the day it was written; only the current source says what is still true.
- **A cap that is exactly hit is a ceiling, not a coincidence.** Five open Dependabot PRs against `open-pull-requests-limit: 5` read as "five updates pending". It actually meant *at least* five, with the rest suppressed and invisible. Regrouping and clearing the queue immediately surfaced six previously-hidden majors. Any bounded queue sitting exactly at its bound should be treated as an unknown backlog, not a known one.
- **The upgrade that looks riskiest can be the one carrying the security fix.** `vitest` 2→4 was the scariest line in the batch — two majors, 57 test files — and had sat untouched nine days for that reason. It was the only bump with security weight: it cleared the sole critical and both moderates (`@vitest/mocker`, `vite`, `vite-node`, `esbuild`). Measure `npm audit` before and after rather than ranking bumps by how alarming the version jump looks.
- **A pinned dependency needs its version-locked siblings pinned too, or the pin leaks.** `next` was exact-pinned and ignored for major/minor, but `eslint-config-next` — which ships in lockstep — carried no rule, so a majors group swept it to 16.x against a 15.x `next`. A pin expressed on one package name is not a pin on the constraint you actually meant.
- **A quality gate that cannot run still reads as configured.** `npm run lint` exits 1 into an interactive "How would you like to configure ESLint?" prompt because the repo has no ESLint config at all — while `eslint` and `eslint-config-next` sit in `package.json` looking like a working setup. Nothing surfaced this for months. Run every declared script once when you inherit a repo; a script that has never been executed is not a gate.

### 2026-08-03 (session-kickoff track)

- **Budget subagent fan-outs against the shared session limit.** The account's usage window is one pool shared by the main loop and every subagent — a 5-agent review batch launched right after a 4-agent research batch killed 4 of 5 mid-run (`session limit · resets 12pm`). Cap concurrent heavy subagents at ~2–3, stagger phases (research → synthesize → then more), use a cheaper model tier for miners/researchers when depth allows, and don't launch a second heavy batch on the heels of a big one. Corollary: tell research agents whether they may sub-spawn — an agent given an N-domain scope will sometimes fan out on its own and stall waiting on children.
- **When two subagent reports contradict each other, read the source — and read it anyway for any claim that shapes the design.** One explorer correctly said `/retry` only re-arms a task; the planning agent said it dispatches (which would have put a security guard on the wrong route). Thirty seconds of reading the 40-line route settled it. Subagent reports are testimony, not evidence: spot-verify every load-bearing claim (what guards what, what runs when) in the main loop before it becomes a plan step.
- **A one-off Node script that imports a repo's dependencies must resolve from inside the repo.** An ESM `.mjs` dropped in a temp/scratch dir dies with `ERR_MODULE_NOT_FOUND` — ESM resolves `node_modules` from the *script file's* location, and `NODE_PATH` doesn't apply. Either place the script inside the repo, or run `node -e '<CJS source>'` from the repo's cwd (CJS `require` in `-e` resolves from the working directory).

### 2026-08-12 (accuracy audit + opener rebuild: usage undercount, SWR, top-N ranking)

- **A one-level glob over a tool's log directory silently undercounts the moment that tool starts nesting per-child logs.** Claude Code writes subagent transcripts *below* the session log — `~/.claude/projects/<proj>/<sessionId>/subagents/agent-*.jsonl`, and one level deeper again for an agent that spawns its own — so a reader globbing `projects/*/*.jsonl` never opened 636 of 857 files and reported **54% of the week's input tokens**. Nothing looked wrong: session counts were exactly right (subagent records carry the *parent* `sessionId`), and output tokens were only 3% low, because uncached session-start turns hold nearly all the input. Walk recursively, and report how many files you actually opened so the number is falsifiable.
- **When your count and the app's count disagree, find the exact signature of the delta before deciding which is wrong.** Don't pick a winner by plausibility. First rule out your own double-counting (dedupe by record uuid: 0 duplicates across 15,905 records proved the walk was clean), then correlate the gap against a candidate cause — sidechain turns 1,100 vs a 1,116-turn gap, sidechain input 382,027 vs a 382,017 gap. Two matches to four significant figures name the cause; a hunch names a suspect. Then confirm it in the source, which is where "the glob is one level deep" actually turned up.
- **Check that the fields you're about to rank or branch on are populated by the query that fetched them.** `gh search prs --json` returns no `mergeable`, `checks`, or `reviewDecision`; the mapping layer sets all three to `null` on purpose. A ranking with a "checks failing" tier would have compiled, passed review, and never once fired. Grep the fetch for the field name before building logic on it.
- **A TTL cache in front of an expensive read guarantees one request per TTL pays the full worst case.** A 60s cache over a ~25s log scan meant one unlucky request a minute ate 25 seconds — and the page polled, so it was reliably broken rather than occasionally slow. Stale-while-revalidate converts that into staleness: serve the cached payload immediately, refresh behind it, de-dupe concurrent refreshes, and only block when there is genuinely nothing to show. Ship `cachedAt` + `refreshing` with it so the UI can say how old the numbers are instead of implying they're live.
- **A stale performance claim in a comment is worse than no claim.** `Reading the local logs takes up to ~1s on a warm SSD` sat above a path measured at 24.6s — off by 25×, and load-bearing, because it was the stated reason the cache TTL was safe. Any comment asserting a duration needs a date and the machine, or it should assert nothing.
- **In Next.js dev, separate route-compile time from real work before optimizing either.** First-hit cost includes JIT compilation, so a "slow endpoint" can be entirely the compiler: `/api/usage` was 3.3s cold against a 3.1s compile (all compiler), while `/api/flow` was 19.7s cold against a 393ms compile (all real work). `grep Compiled` in the dev-server log tells you which before you spend an afternoon on the wrong one.
- **A "top N" list must never pad itself to N with stale filler.** Ranking open work by recency put 2014 university-coursework PRs (4,302 days stale) in three of six rows and pushed the current week off the bottom. Demoting them to a lower tier wasn't enough — with fewer fresh items than slots, the padding reappeared. Exclude beyond an age floor and report the excluded count ("plus 8 untouched for over 6 months"), so the tail stays visible without occupying the surface.
- **A flex row can clip its last child while the document reports no horizontal overflow at all.** Adding a fourth nav tab pushed "Analytics" behind an absolutely-positioned pill: unreachable, no scrollbar, no ellipsis — and `document.scrollWidth === document.clientWidth`, so the standard no-horizontal-scroll assertion passed. Measure the *container's* `scrollWidth > clientWidth`, and confirm the last child's rect actually falls inside it.
- **Never measure layout in a viewport whose `clientWidth` is 0.** A hidden or freshly-navigated preview pane reports `0x0`, which makes every element "overflow" and every overflow check fail. Two consecutive readings were garbage before the zero was noticed. Assert a plausible viewport width first, then measure — and re-pin it after every navigation or reload, because the pane collapses again.
- **BSD `find` has no `-newermt`** (nor `-newerXY` with a date string). On macOS `find … -newermt "-2 days"` doesn't error usefully — it just matches nothing, which reads as "no such files". Use `-mtime`, or filter with `stat`.
- **Don't diagnose a stuck UI on a page that has been hot-reloaded a dozen times.** A component wedged in its loading state through 12 Fast Refresh cycles looked exactly like a real fetch hang; one clean reload rendered it correctly. Check the console for the reload count and reload before opening the debugger.
- **A single `status: "ok" | "unavailable"` on a read that fires N independent queries is a lie by construction.** Both GitHub connectors return `"ok"` when *either* half succeeds — that's deliberate, so one failure doesn't blank the other — but four consumers then read only `status` and rendered the failed half as a confident zero: `0 PRs merged` for a count never fetched, `0 issues` for a search that errored. Availability has to be **per count** (`pullsOk` / `issuesOk`, surfaced as `null` and drawn as an em dash), not per source. Sharpest detail: this session *wrote the "unread must never render as zero" rule into AGENTS.md* and then broke it four times in code written an hour later, and Codex caught it by citing that very line back. Writing the rule down does not implement it — grep your own new payloads for it before opening the PR.
- **Adding a null-able count to a non-null one silently reports the surviving half as the total.** `openPulls + openIssues` with one side null yields either a number that's wrong or `NaN`, depending on types. A derived total must be null unless *every* input to it was read.
- **Stale-while-revalidate has a client half, and shipping only the server half is worse than no SWR.** Answering a stale request instantly with `refreshing: true` obliges the client to come back for the rebuilt payload. A one-shot `useEffect` never does, so that browser sits on the old numbers under a permanent "refreshing" label until the user navigates — a spinner that never resolves, which reads as a hang. Schedule a bounded follow-up poll while `refreshing` is true, and clear it on unmount.
- **The "a cap exactly hit is a ceiling" rule has to be applied to every count in a payload, not once per session.** `gh search` caps each category at 30; a category sitting on 30 is an unknown backlog. The same PR that correctly rendered "14 further items beyond the per-project cap" for a backlog file presented the GitHub counts as exact totals. Render `30+` whenever a list came back at its limit, and compare against the *raw* row count, not the filtered one — a row dropped in mapping still consumed a slot.
- **Don't conclude "no bot review yet" from a one-minute poll, and don't read `gh pr checks` as the answer.** Codex arrived several minutes after the PR opened, well past two 25s polls. `gh pr checks` said "no checks reported on the branch" the whole time, which is orthogonal — this repo has no CI at all. The reviews live at `gh api repos/O/R/pulls/N/comments --jq length` and `gh pr view N --json reviews`; a recent PR with zero Codex comments is also not evidence the bot is off, since it stays silent when it has nothing to say.

### 2026-08-14 (client-side caching, cross-tool session reader, dashboard simplification)

- **A cache write placed inside a "did my component unmount?" guard silently exempts exactly the requests that needed caching most.** The guard exists to skip `setState` after unmount; putting the `cache.set` behind it too meant any request that outlived its component contributed nothing. The bias is perverse and invisible: the *slower* the endpoint, the likelier you navigate away mid-flight, so a 20 ms route cached every time while a 16–25 s git sweep never cached once — and the tab that most needed the cache was the only one that never got it. Cancellation is a statement about the component, never about the payload; write to any shared store *before* the guard, and let the guard cover only the React updates.
- **Seeding React state from `sessionStorage` in a `useState` initialiser breaks hydration, and the repro needs three steps so you will not stumble into it.** Page A caches, navigate to page B, then *reload B*: the server renders empty, the client's first render reads the persisted payload, and React reports "Hydration failed" and discards the whole server tree. The distinction that makes it tractable: a **module-level** cache is safe to read during render (only this document's fetches populate it, so it is empty exactly when the server's view is), while **`sessionStorage` outlives the document** and can hold state the server never knew about. Seed from memory synchronously, promote the persisted copy in an effect.
- **A console that has accumulated a session's worth of broken intermediate states hides real errors as effectively as it invents fake ones.** Chrome retains console output across same-tab navigations, so mid-edit syntax errors — long since fixed, tree typechecking clean — kept resurfacing and made a *genuine* hydration failure look like more of the same. Clearing storage did not help, because it was never a storage problem. **A fresh tab is the discriminator**, and it earns its keep in both directions: it proved one page clean and surfaced the real bug the noise had buried. Sibling of "don't diagnose a stuck UI on a hot-reloaded page".
- **`tsc --noEmit` passing is not evidence a client bundle builds.** A `"use client"` component that *value*-imports from a module touching `node:fs` typechecks perfectly and dies at bundle time with `UnhandledSchemeError: Reading from "node:fs"`. A bare `import type` is erased and safe; importing one constant alongside it drags the filesystem reader into the browser. Keep shared types and display constants in a `.types.ts` sibling that imports nothing, and have the Node-side module re-export them — the boundary then survives someone later adding a value import.
- **When a slice of a file is parsed line-wise, which edge is a fragment depends on which slice it is — and getting it wrong loses data silently rather than erroring.** Reading a bounded head + tail to avoid a 163 MB scan: a truncated head ends mid-line (drop the last), a tail of a larger file starts mid-line (drop the first), and a file read *in full* has no fragment at either end (drop neither). Unconditionally dropping the last line discarded the newest record of every small file — precisely where a session's final title and last prompt live. Pass the two edge flags explicitly; never infer them from one boolean.
- **A synchronous test cannot be interrupted by a test-runner timeout, so a sync test near the limit is a coin flip decided by machine load.** A 9 s `execFileSync` fixture against a 5 s default passed on an idle checkout and failed with a running dev server, on a byte-identical file — which reads as "the branch broke it". Any deliberately slow test needs an explicit timeout, and any duration written in a comment needs a date and a machine or it will quietly become a lie (this one claimed "~7s").
- **Ask what fraction of a surface is rendering true-but-useless zeros before redesigning it.** A dashboard rebuilt to escape "thirty rows of zeros" still opened on six cards reading `0 pending · 0 active · 0 done`, because **1 of 30 projects had ever dispatched a task** — plus a permanent paragraph above defining vocabulary almost nobody encountered. A zero that is genuinely zero costs nothing to hide and returns the moment it means something; the measurement (1/30) is what turns a taste argument into a decision.
- **Ranked lists and headline tiles duplicate each other the moment both are fed by the same ranking, and adding the good one is what creates the duplicate.** A new "Start here" panel put its top items 120 px above a "Top TODOs" list drawn from the same source — 2 of 2 items repeated — and a fifth stat tile restated a count that the row beneath it already carried in its collapsed summary. After adding any summarising surface, diff its contents against what is already on screen; the regression is authored by the improvement.
- **Look for the pattern the codebase already settled on before importing one from outside.** Researching how other developer hubs organise a dashboard converged on "one verdict, ~3 ranked items, evidence on demand" — which the app's own Analytics → Flow tab had already implemented (four headline numbers, then collapsed rows whose summary lines carry their answer), alongside a house `Disclosure` component documenting the rule that a collapsed row must show enough that you never open it just to decide whether to. The external research was useful for confirming the shape, not for supplying it.
- **A nav row that scrolls is not a nav row that is discoverable.** At the app's primary 375 px viewport the last of four tabs sat entirely outside the visible strip: `overflow-x: auto` made it reachable by dragging, so an earlier fix had declared the clipping solved, but nothing on screen suggested a fourth tab existed. `document.scrollWidth === clientWidth` throughout — only the nav container's own `scrollWidth > clientWidth` shows it. Budget the row in pixels (238 px needed vs 180 px available) and reclaim the deficit from whatever is largest; here a status pill's countdown, hidden below `sm`, freed 84 px and kept both the headline figure and the full `aria-label`.
